# ContriPact — 产品需求文档（中文版）

一个面向比赛团队的轻量 AI 贡献治理体验：帮助团队在项目开始前先约定“哪些工作真正重要”，或在项目结束后依据比赛规则与实际证据评估贡献，从而降低成员因为面子、关系、礼貌和操守而难以直接争论“谁贡献更大、谁应该拿更多”的社交成本。

来源：`scope.md > 独特核心`、`scope.md > 核心循环`、`scope.md > POC 边界`。

## 核心用户旅程

1. 用户先进入一个商业化的 ContriPact 首页。整体是黑白 + 水墨视觉，默认英文，并提供清晰的中文切换。首页不把团队关系写成负担，而是直接指出两种都合理的价值发生了张力：贡献应该影响收益，信任和凝聚力也必须被保护。ContriPact 的作用，是让团队不必为了维护关系而牺牲贡献激励，也不必为了强调贡献而伤害关系。
2. 首页主按钮直接进入一个准备好的 4 人比赛案例，奖金池为 ¥12,000。
3. 同一个案例里有两个模式：**项目开始前（Before Project）** 和 **项目结束后（After Project）**。
4. 在 **Before Project** 中，系统展示准备好的比赛规则与评分标准，提取最影响结果的关键标准，把计划中的任务映射到这些标准，并判断哪些任务可能属于高价值贡献，同时解释原因。
5. 团队可以检查这张“贡献地图”并确认同意。这里的目的不是提前分钱，而是先约定“什么样的工作算高贡献”。
6. 在 **After Project** 中，系统展示同一份比赛规则，以及四名成员实际完成的贡献与证据记录。
7. AI 根据比赛标准和之前确认的贡献地图评估各项实际贡献，突出最关键的贡献点，并解释为什么这些工作对最终结果重要。
8. 系统据此给出 ¥12,000 的贡献型奖金建议，并把每个人的建议比例与具体理由、证据直接连起来。
9. 一名成员可以提出异议，并填写简短理由。
10. AI 判断这个理由是否真正关联到比赛规则、实际证据或之前确认的贡献标准；如果异议成立，就调整建议；如果不成立，就说明为什么维持原判断。
11. 最后由团队确认当前方案。结尾必须明确：AI 做的是贡献相关性判断与建议，真正同意方案的人仍然是团队。

## 页面与布局

### 1. 商业首页

来源：`scope.md > 视觉与身份` + 用户已确认设计方向。

- 首屏是商业 Hero，不是内部管理后台。
- 视觉以黑、白、暖白和水墨为主。
- 鼠标移动时，背景产生克制的水波 / 墨迹扩散效果。
- 艺术效果不能拖慢进入产品：价值主张和主按钮必须首屏就能看到。
- 首页不只讲“大家不好意思比较贡献”，而是强调两种正向价值的冲突：**贡献决定激励，信任决定凝聚力**。
- 英文主标题：**Reward contribution. Protect the team.**
- 英文副文案：**Contribution fuels progress. Trust holds a team together. When rewarding impact starts to threaten that trust, ContriPact turns awkward personal judgments into shared, evidence-backed decisions.**
- 中文主张：**让贡献值得回报，也让关系不必为此受伤。**
- 中文副文案：**贡献推动团队向上，信任让团队凝聚。当按贡献分配与维护关系发生张力时，ContriPact 用规则、证据和 AI 辅助判断，把难说出口的话变成团队可以共同确认的决定。**
- 一个主要按钮直接进入准备好的 Demo 案例。
- 首页提供 English / 中文切换；默认 English，切换语言不重置 Demo 状态。

### 2. 贡献治理工作台

来源：`scope.md > 核心循环`、`scope.md > 60 秒成功标准`。

整个 Demo 尽量压在一个核心工作台里完成。视觉沿用现有 ContriPact：宋体 / serif 标题、克制的黑白卡片、证据导向标签、明确阶段感，但不复制生产版账号和导航复杂度。

工作台包含：
- 比赛背景与 ¥12,000 奖金池；
- **Before Project / After Project** 模式切换；
- 比赛规则与评分标准；
- 贡献价值分析区；
- 成员级理由与证据；
- After 模式中的奖金建议；
- 异议 / 理由判断区域；
- 最终确认状态。

## 视觉与体验

- 保留现有 ContriPact 的核心视觉：**黑白 + 水墨 + 现代 SaaS**。
- 商业首页要比现有内部项目 Dashboard 更有艺术感和品牌感。
- 鼠标水波 / 墨迹扩散是标志性交互，但不能挡文字、拖慢 CTA 或变成游戏特效。
- 工作台应该显得冷静、严谨、证据导向、中立。
- 大标题使用 editorial / serif / 宋体气质；数据、标签、操作使用干净无衬线字体。
- 避免常见 AI 霓虹风、过度渐变、金融交易终端感、卡通“公平秤”隐喻。
- 产品本身做中英双语：默认英文，提供中文切换。不要所有组件都并排放两种语言，以免破坏水墨与留白感。

## 功能与行为

### 商业入口

来源：`scope.md > 视觉与身份`。

首页在进入案例前要让用户迅速理解三件事：
- **按贡献获得回报**和**维护团队信任与凝聚力**都是合理目标，真正的问题是二者发生张力时，团队容易被迫妥协其中一个；
- ContriPact 会读取比赛规则，并把规则连接到真实工作，让贡献讨论围绕共同标准，而不是成员之间直接互相比较地位；
- AI 会给出有理由的建议，但最后还是团队同意。

产品采用中英双语。因为比赛提交环境以英文为主，所以默认 English；中文用户可以切换到完整中文版，但两种语言保持同一套流程与状态。

验收标准：
- [ ] 评委不需要长时间滚动，就能理解 ContriPact 解决什么问题。
- [ ] 主按钮能直接进入准备好的 Demo 案例。
- [ ] 鼠标波纹 / 墨迹效果会响应移动，但不阻挡文字和主要操作。
- [ ] 默认语言为 English，并有清晰的“中文”切换入口。
- [ ] 切换语言不会重置当前案例、模式或异议状态。

### 比赛规则分析

来源：`scope.md > 独特核心`。

工作台展示一份准备好的比赛说明，并提取少量关键评分标准。每条标准包括：
- 标准名称；
- 相对重要性 / 相关性指示；
- 一句为什么它会影响比赛结果的解释。

验收标准：
- [ ] 用户能看出这些标准确实来自比赛说明。
- [ ] 在评估任何个人贡献前，用户已经能理解至少一条标准为什么重要。

### 项目开始前：贡献规划

来源：`scope.md > 核心循环 > 项目开始前模式`。

系统把准备好的计划任务映射到评分标准，并在项目开始前判断哪些工作更可能带来高竞赛价值。

每个计划任务显示：
- 任务 / 职责；
- 对应的一个或多个评分标准；
- 预期贡献价值（例如 High / Medium / Supporting）；
- 基于规则的简短理由。

团队可以确认这张贡献地图，作为后续判断的共同参考。

验收标准：
- [ ] 至少一个任务被明确识别为高价值，而且理由直接关联评分标准。
- [ ] 用户在没有看到奖金分配前，也能分清核心高价值工作和支持性工作。
- [ ] 团队可以把这张地图标记为已同意。

### 项目结束后：贡献评估

来源：`scope.md > 核心循环 > 项目结束后模式`。

同一个案例切换到实际贡献记录。每名成员显示：
- 主要贡献；
- 证据 / 产出摘要；
- 对应评分标准；
- AI 评估的贡献价值；
- 为什么这项贡献对最终结果特别重要或并非核心贡献的解释。

验收标准：
- [ ] 每个人的判断都引用可见的规则或证据，而不是只给一个分数。
- [ ] 评委能看懂为什么不同工作会得到不同贡献判断。

### 奖金建议

来源：`scope.md > 60 秒成功标准`。

完成贡献评估后，系统给出 ¥12,000 的建议分配。

每名成员显示：
- 建议百分比；
- 建议金额；
- 与贡献价值相关的简短解释；
- 明确区分“证据事实”和“AI 对证据的解释”。

整个结果必须被标记为“团队可讨论的建议”，不能写成“客观公平答案”。

验收标准：
- [ ] 百分比总和 = 100%，金额总和 = ¥12,000。
- [ ] 每人的建议都能追溯到可见贡献理由。
- [ ] 文案不得声称 AI 已经算出客观公平分配。

### 异议与理由判断

来源：`scope.md > 独特核心`、`scope.md > 项目结束后核心循环`。

成员可以对当前建议提出一次异议，并填写简短理由。

系统判断该理由是否真正引用到：
- 比赛规则 / 评分标准；
- 实际贡献证据；
- 项目开始前已经同意的贡献地图。

结果需要显示：
- 异议是否被当前上下文支持、部分支持或不支持；
- 使用了哪条规则或证据做判断；
- 是修改奖金建议，还是解释为什么维持原建议。

验收标准：
- [ ] 系统不能只显示“AI 不同意”。
- [ ] 理由判断必须引用可见的规则 / 证据。
- [ ] 只有当解释明确表明异议改变了贡献判断时，奖金建议才变化。

### 最终确认

来源：`scope.md > 核心循环`。

团队可以确认当前方案为最终接受结果。最终状态显示：
- 最终分配；
- 贡献理由已经被检查；
- 最后接受方案的是团队，而不是 AI。

验收标准：
- [ ] 最终页面清楚区分 AI 建议和团队同意。
- [ ] 接受状态足够明确，可以作为 60 秒 Demo 的结束画面。

## 状态与边界

- **Landing** — 商业 Hero + 进入 Demo。
- **Before analysis** — 比赛规则、计划任务贡献地图；不显示奖金。
- **Before agreed** — 贡献地图已作为团队共同参考被确认。
- **After analysis** — 实际证据、AI 贡献判断、奖金建议。
- **Objection open** — 某成员提出异议，理由等待 / 正在展示判断。
- **Recommendation revised or defended** — 系统解释为什么调整或维持建议。
- **Final accepted** — 团队接受当前方案。
- **Analysis unavailable** — 如果 AI 分析失败，仍保留原始规则和证据，不生成假的推荐结果。

这个 POC 不需要账号状态、项目持久化、邀请码状态或多浏览器协同状态。

## 产品决策

- 沿用现有 ContriPact 的视觉与治理身份，但不复制完整生产流程或旧代码。
- 主要产品问题是：成员很难公开比较彼此贡献，而不是“怎么算百分比”。
- 同一个案例同时有 Before / After 两个时间点，让评委在一次 Demo 中看懂“事前规划 + 事后评估”。
- AI 判断的是**某项贡献和比赛结果的相关性 / 价值**，而不是人的道德价值或所谓客观公平。
- 比赛规则和可见证据是 AI 判断的主要依据。
- Before 模式生成贡献地图，不提前分钱。
- After 模式因为已有实际贡献证据，所以可以给奖金建议。
- POC 只做一次异议；目的是证明“可以质疑 AI”，不是做完整仲裁平台。
- 最终决定权保留在团队手里。

## 本次要做的内容

- 商业化水墨首页 + 克制的鼠标波纹效果。
- 一个准备好的 4 人比赛场景。
- 一份准备好的比赛规则与评分标准。
- Before / After 模式切换。
- Before：计划任务 → 评分标准 → 贡献价值规划。
- After：证据 → 贡献价值评估。
- 可解释的 ¥12,000 奖金建议。
- 一次异议理由判断。
- 调整 / 维持建议的解释。
- 最终接受状态。
- 整条链路可以在 1–3 分钟比赛视频中完整展示，并让评委约 60 秒理解核心价值。

## 本次不做，但属于完整产品

- 登录、真实账号、项目创建、邀请与角色权限。
- Supabase / 正式数据库持久化。
- 实时多人协作。
- 完整 Peer Review 流程与透明评分账本。
- 任意比赛文档上传 + OCR / parser。
- 项目进行中的连续贡献记录。
- GitHub / Figma / Docs Evidence connector。
- 多轮异议、调解和完整审计历史。
- 多套分配 policy 与实体奖品匹配。

这些仍然属于完整 ContriPact，只是不值得在 Build With AI 这个 2–4 小时 POC 中重做。

## 后续可能增强

- 上传任意比赛规则后自动生成贡献地图。
- 接入真实项目证据源，持续更新贡献信号。
- 对比项目开始前的贡献地图和实际结束后的贡献结果。
- 多个成员分别提异议，并通过 consent-based 流程 Final Lock。
- 对不同类型工作做模型一致性 / 偏差测试。

## 非目标

- 重做完整现有 ContriPact 生产产品。
- 宣称 AI 能客观决定公平。
- 给人本身排价值等级。
- 把规则和证据隐藏在一个不可解释总分后面。
- 为本次 Hackathon POC 建完整生产协作基础设施。

## 未解决问题

目前没有会阻止进入 Technical Spec 的产品级问题。

“具体用哪个模型”“比赛规则分析是现场生成还是预计算”“鼠标水墨波纹怎么实现”都属于 `4-spec` 的技术问题，而不是 PRD 产品行为问题。
